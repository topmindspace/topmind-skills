# 公众号改稿规则（Stage 1 执行标准）

从技术博客 Markdown 到公众号稿，改的是**阅读节奏**，不是技术事实。事实、数据、链接一律不动。

## 必须做

1. **开头 150 字内给钩子**：结论、反差或悬念，不要背景铺垫。原文首段若是长背景，压缩或后移。
2. **段落切分**：单段 ≤ 110 字（约 4 行手机屏）。长段按语义断点拆开，不要机械等分。
3. **小标题序号化**：二级标题统一「一、二、三」或「01 / 02」，读者能感知进度。
4. **列表项 ≤ 70 字**：超长列表项改成「加粗小标题 + 短说明」的段落组。
5. **重点加粗**：只加粗结论句和关键数据，全篇加粗密度控制在每 20 字不超过 1 处。
6. **长句拆短**：单句 > 45 字且有逗号堆叠时，拆成两句。
7. **图注统一**：`*▲ 图 N：说明*`，图注要说出「看什么」，不要只重复图片名。
8. **外链处理**：保留可点性无意义，改为「来源：XXX（URL）」的灰色小字或直接写机构名。
9. **结尾三段式**：一句总结结论 → 一句抛出问题/邀请讨论 → 引导关注语。

## 不要做

- 不改技术事实、不改数据、不改评测结论
- 不删代码块（公众号读者需要可复制的配置/命令）
- 不把「我」改成「笔者」「作者」等腔调词，第一人称是这类文章的信任来源
- 不加「随着...的发展」「在当今时代」这类 AI 腔 / 八股开场
- 不加 emoji 堆砌的小标题
- 不为了凑字数注水，公众号长文 3000-6000 字是合理区间
- 中英文/数字之间忘了空格没关系（lint --fix 会补），但**别手动在代码和链接里加**

## 容器语法使用时机（v2）

| 时机 | 用法 |
|---|---|
| 一句话核心观点、想让它从版面上跳出来 | `::: pull` 金句容器（大字居中，前后留白） |
| 关键数据对比（如「62.7% vs 99.9%」） | `::: stat` 数据卡（大数字 + 注释） |
| 补充但不打断主线的信息 | `::: note` 灰色提示框 |
| 操作建议、经验窍门 | `::: tip` 绿色提示框 |
| 容易踩的坑、官方风险提示 | `::: warn` 橙色 / `::: danger` 红色 |
| 观点交锋、问答式段落（A: B:） | `::: dialogue` 对话容器 |
| 版本号、状态标签、关键词打标 | `[!新特性]` 行内徽章 |
| 全文最重要的 1-3 句 | `==高亮==`（节制使用） |

原则：**每 800 字最多 1 个容器**，容器是调味料不是主菜；连续两种容器相邻会显得杂乱。

## 去 AI 腔检查点

- 排比三连句（"不是 A，不是 B，而是 C"）出现超过 2 次 → 改写
- 「值得注意的是」「综上所述」「不难看出」→ 删
- 每段都以「首先/其次/最后」开头 → 打散
- 形容词堆叠（"极其轻巧稳定的架构"）→ 留一个

## 排版参数基线（调研印证的通用规范）

- 正文 16px、行距 1.75、字间距 0、左对齐（不用 justify，会被格式检测判为非标准值）
- 段间距 22px 代替首行缩进（手机端惯例）
- 正文色 #333（纯黑 #000 在白底上过刺眼），辅助文字 #888
- 代码块深底浅字（浅灰底代码块在部分安卓机型上对比度不足）

## 交付前自检

```bash
python3 scripts/lint-wechat.py --input 公众号稿.md --fix
```

错误项（长段 > 200 字 / 图片缺失/过大）必须清零；警告项逐条判断是否接受。
